# Assistant sources

How the assistant finds text, keeps it in each person's rights, and shows where every line came from; how chats are labelled, shown in two languages and deleted; and how names are masked before a hosted model sees them. Rules in the AI sources, Assistant chats, Name variants and Record passages sections of `drizzle/0000_baseline.sql`; `src/jobs/index-documents.ts`, `src/services/assistant.ts`, `src/services/masking.ts`, `src/services/document-summaries.ts`; the AI service's `POST /v1/embed`, `/v1/answer` and `/v1/summarize`. The design and its reasons: https://claude.ai/artifact/FTRTXVTCLqgRjgwbCsCVDW.

No model has been run for any of this: the tests use fake vectors and a fake summariser, and nothing runs on the server yet.

## The search index

One index (`ai_chunks`), built from each file's original text in whatever language it is written. The embedding model is multilingual, so an Arabic question finds English text and the other way round; nothing is translated before indexing.

`npm run job:index-documents` runs as the schema owner. It takes files that have the AI flag on, are scanned clean (or skipped) and not archived, and are still `pending`:

- Files are read by page (`src/jobs/extract-text.ts`). Text files: a form feed starts a page. PDF: `pdftotext` (poppler, installed in the jobs image), fed on stdin with a time and size limit; Arabic set in presentation forms is folded back to ordinary letters, direction marks are dropped, and the lam-alef that poppler writes in reverse after the article ("اإلدارة") is put right. A plain reversed lam-alef ("خالل" for "خلال") can't be told from real text and stays; the multilingual embedding still finds the passage, and the cited page shows the real words. Word: the page marks Word saved when the file was last laid out, or explicit page breaks when there are none, with tables one row per line. PowerPoint: a slide is a page, in the order the presentation shows them (speaker notes are left out). Excel: a sheet is a page, starting with its name. Office files go through the same zip and XML readers as the plan import, with the same limits.
- Passages are at most about 1,200 characters, split at blank lines, then lines, and never across pages. Each passage keeps its page, and copies the file's project, label, department and (for a private file) its owner.
- A PDF page with fewer than 20 letters has no text layer: it is a scan. Its number goes in `ocr_pages` for text recognition later, and the rest of the file is indexed. A file with nothing but scans (and any image) is marked **needs text recognition** (`needs_ocr`), not "not searchable", so it can be picked up when recognition comes. The file panel lists the scanned pages.
- A file that can't be read (damaged, encrypted, a refused archive) is marked **not searchable**, so the screen can say so instead of the file quietly missing from answers. A file that can't be fetched from storage, or a PDF when `pdftotext` is missing, waits for the next run.

**Recommendations and actions** (baseline: Record passages) are indexed by the same job, one passage each: a recommendation's title, rationale, expected outcome and required evidence; an action's title, description and its recommendation's title. The passage takes its recommendation's label, and is read only by someone who can read the record itself (the `with_source` policy), so a client never finds a firm-only recommendation or a draft action (D6: for a client scope the search also checks the action's status inside its `WHERE`), and a department's action stays in it. A change to that text, a change of label, or deleting the record drops the passage, and the next run writes it again; a save that changes nothing keeps it. One passage per record, even when two runs overlap.

Only the job sets a file's text status and its scanned pages. Turning the AI flag on, a change of visibility and refiling to another department drop the file's passages and set it back to pending, so it is indexed again.

## Searching

Hybrid search, in Postgres only. No graph database and no graph RAG: Selah's links (finding → recommendation → actions → evidence → review) are foreign keys, few and always the same, so a SQL join walks them under the same row-level security as everything else.

1. **By meaning:** the 20 nearest passages to the question's vector (`ai_chunks.embedding`, HNSW).
2. **By words:** the 20 best keyword matches (`ai_chunks.tsv`, GIN, the `simple` configuration so Arabic words are kept as written). The question becomes an OR of its distinctive words (`keywordQuery()`), letters and digits only, so nothing typed can change the query's syntax. This finds exact terms the vectors blur: an article number, a policy code, a name.
3. **Merged** by reciprocal rank fusion (`fuse()`), keeping 8. Passages of the chat's case come first.
4. **Records found by the search**: the same two searches over recommendation and action passages only, keeping 3, so a record never takes a file passage's place. What the model gets is the record as it stands now, not the indexed text.
5. **Linked records** (`linkedRecords()`): the chat's case, the records the search found, then the recommendations (through their findings' source file) and actions (through their evidence) behind the files found. At most 4, each a few lines: a recommendation's priority, due date, rationale, expected outcome, required evidence and actions; an action's status, due date, last review and last progress update. They go to the model as passages like the others and can be cited (a citation with no `chunkId`).

Both searches carry the full permission filter in their `WHERE`; the linked records are read under row-level security.

## Filtering

Rights are applied before retrieval, never by a model:

1. `retrievalScope()` (the same `authorize()` as the rest of the app) gives the project, client and labels. It goes inside the vector query's WHERE clause.
2. Who sees an item (feature A, migration `0095`): a passage of a file, or of a meeting's note, that the person is left out of is excluded inside the same WHERE (`app_audience_ok`), never filtered afterwards, so a left-out person's question can never retrieve it and no citation can point to it.
3. The query runs under row-level security. A file's passages are read only by people who can open the file, while it is open to the assistant and not archived, whatever the passage's own label says; the restrictive policy `audience` on `ai_chunks` leaves out the same passages again.
4. Only what survives goes to the model.

`tests/db/ai-sources.test.ts` checks this for every test user in every project, with their real scope and with a forged one asking for every label: every passage that comes back is from a file that person can open. `tests/db/audience.test.ts` checks that a person left out of a file gets none of its passages, with their own scope or one naming someone else, and that its title is not found for a citation.

The masking lists (`app_mask_terms`, `app_mask_terms_in`) hold names only, never a file or a meeting, so they need no audience check.

## Attaching a file

The owner's request (lead-log, "Progress report change"): typing `@` in the assistant's box opens a list of Selah files the asker can already open, and picking one attaches it to the question. No new model, service, index or migration: the file's existing passages are used.

- **The picker** (`GET /api/assistant/files?project=&q=&locale=`, `attachableFiles()`): the files `listFiles()` gives the person (row-level security, then `authorize("document.download")` with its shares and who sees it: the Files card's own check), current versions only, not archived, in the chat's project or, in a chat across projects, in every project the person may ask about (`retrievalScope()`, as a question). Names are matched in the database, in either spelling, with the person picker's folding on both sides (`foldName()`, `src/lib/person-match.ts`: case, Latin accents, short vowels, alef forms, ى and ة; `titleHas()` in `src/services/files.ts`), so an old file is found as well as a new one; the listing is the light one (no evidence, assessment or meeting lookups) with the same visibility, at most 40 rows read and 8 shown a search (review S2). A project the person may not ask about answers Not found, so an action owner gets nothing. Only names and states, never text.
- **The chips.** A picked file shows as a chip above the box, with a button to take it off; at most 3 a question (`MAX_ATTACHMENTS`, `src/lib/assistant-attach.ts`). A file the assistant can't read says why on its chip, from the file's own state (`attachStatus()`): "Not available to the assistant" (the switch is off, which includes every answer to a confidential request, migration 0106), "Not indexed yet" (`pending`), "Scanned pages only" (`needs_ocr`), "Its text can't be read" (`not_searchable`). Nothing from such a file is sent.
- **On send** (`attachments` in `POST /api/assistant/query`, ids only), `attachedPassages()` in `prepareAsk()` checks each id again, in the question's own transaction and as the person: the file must be one `listFiles()` gives them in the chat's projects. Any other id (a file they can't open, another client's, another project's, an old version, one that doesn't exist) is "gone", and the model gets exactly what it would with no attachment: no hint that the file exists. A visible file is read only when it is open to the assistant and its text status is `searchable`; then its passages nearest the question (at most 6 across the files, shared between them) are read through `scopeFilter()` (labels, departments, who sees it, the client's allowed sources) under the same row-level security as the search. One with no passage left to give is "not available". Stale passages of a file that is off, pending or scanned are never read.
- **Where they go.** The attached passages go first, labelled "attached by the person", and the question says so ("The person attached a file to the question: passage P1."); a chat's own record follows them. They take the place of searched file passages, never of the records, and count toward the 12 passages the AI service takes: they get only what is left after the chat's own record and a status question's rows, keeping one passage free (review S1), so "what is overdue?" with a long file attached still lists all 8 late actions; when the rows fill the question, the file is not read and says so ("crowded"). They are cited like any passage (file, version, page), masked like everything else when masking is on, and every client rule applies to the answer unchanged (the client filter, legal facts without rulings, refused drafts).
- **Never with a draft.** A progress draft is built from the actions only (staff: migration 0110), so it reads no attached file ("draft"); a client person's other draft is refused before anything is read, and each attached file says "draft" too (review N1).
- **What comes back.** The answer (and the streamed `done` line) lists each attached id with what became of it; the card says so in a notice for a file not read. The audit entry records how many files were attached and passages used, and for a client person the passage ids sent, as before. The attachment itself is not stored with the message; the citations are.

Proven by `tests/db/assistant-attach.test.ts` (a visible indexed file goes first for staff, a client admin and a department-limited manager, is cited, and keeps within the limit; masked when masking is on; firm-only, another department's, left out with the picker, another client's and another project's files are "gone" and the model gets the same passages as with an id that doesn't exist, while those who may see them get them; switched off, confidential, pending and scanned files send nothing even with stale passages planted; a progress draft reads none; the picker lists only what the person can open, in either spelling) and `tests/assistant-attach.test.ts` (when the picker opens, what picking does to the text, the chips and their reasons, the list, in both languages).

## Answers

Each chat message is stored once with its language (`ar` or `en`). Messages from before the column were labelled from their script when it was added. An answer is shown in the other language through the translation cache (docs/translations.md), and only its owner can read either. An answer's citations name the file, its version and the page, or the record.

When passages disagree (an approved version and a newer draft, say), the model gives each version with its citation and says which one the passages call approved, newer or a draft; it doesn't pick one silently or refuse. Passage ids such as `[P2]` are taken out of the answer's text, since the sources are listed under it. Under `language: "auto"`, "I can't confirm" is in the question's language, like answers.

Hosted APIs don't all honour `response_format` (Ollama's cloud accepts it and ignores it), so the prompt asks for JSON too, and the AI service takes the JSON object out of the reply (a code fence or words around it are fine) and asks once more if there is none.

A small model sometimes stops after its heading ("The following actions are overdue across the clients:") or in the middle of its first item, and still marks the answer grounded with citations (phase 3 runs B and C, 4 times in 164). The AI service asks once more, with a note asking for the whole answer, when a grounded reply is only that: nothing left once passage markers, formatting and punctuation are taken out; a colon with nothing after it (Markdown, quotes and direction marks at the end are ignored); or a "(" or "[" left open (`unfinished()` in `services/ai/app/prompt.py`). Short answers are whole answers, however they end: "نعم", "12", "2026-03-01", "SAR 250,000", "خالد", "**Quarterly**". If the second reply is still only a heading, `check_answer()` makes it ungrounded, so the person reads "I can't confirm" instead of a heading and its sources. The streamed answer does the same before its last line, unless it already asked again because the reply was not JSON: a stream is at most three model runs (the stream, then one `chat_json` with its own one retry).

**Status questions.** Search finds what files say, not which actions are late. A question about the state of the work ("what is overdue?", "what is blocked?", "awaiting review", "due this week", "what is still open", and the Arabic forms such as "المتأخرة", "المتعثرة", "بانتظار المراجعة", "هذا الأسبوع", "لم تنجز") is noticed by `statusIntent` (`src/lib/assistant-search.ts`), and `statusRecords` then reads the project's actions under the person's row-level security: a count as of today (open, overdue, blocked, awaiting review, sent back, due in 7 days), up to 8 matching actions with their due date, days overdue, owner and blocked reason, and up to 3 recommendations past their date with open work. These go to the model as records it can cite (the count cites the project), and only 4 file passages go beside them. Other questions are unchanged. Draft, verified and closed actions are not counted as open. Found in the GPT-OSS run, where "what is overdue?" was answered from a file's dates instead of the actions.

**Indicator questions.** A question about the client's business indicators ("how are our KPIs against target?", "ما آخر قيمة لمؤشر الشكاوى؟") is noticed by `indicatorIntent`, and on a client project `indicatorRecords` reads up to 6 of the client's active indicators under the person's row-level security: baseline, latest value and period, better or worse than the baseline, target and how far along, missing periods, and the shared recommendations of the project linked to each. A client manager gets only the company's and their own departments' indicators, an action owner none. Each passage says the figures are client-reported, not verified impact, and citations open the indicator's page. A recommendation's record also names the indicators linked to it that the person can see (docs/metrics.md).

A follow-up gets the chat's last 8 messages as context (`history`). They are never sources: the model is told not to cite them, and every turn searches again under the person's rights as they are now. Messages can't be edited by anyone (`UPDATE` is revoked).

## Chats

Every chat belongs to one person, and either to one project (`ai_conversations.project_id`) or to every project the person may ask about. Picking another scope starts another chat.

**All my clients (2026-10-25).** The card starts on "All my clients" (a client person sees "All your projects"), so a vague question ("what is overdue?", "which client is furthest behind?") needs no project; the picker still narrows to one project. Nothing new becomes readable:

- The projects are those the person can open where `retrievalScope()` gives a scope, project by project, the same check as one project. The search's `WHERE` is those scopes joined with `OR`, one tenant per project, under the same row-level security. A client person's projects are all their own organisation's; an action owner still gets no retrieval.
- Every passage the model reads says which client and project it is from, and those labels are masked like the text. The sources under an answer name the client and project too.
- A status question gets a count across the projects with a line per client and project (the projects with most overdue first), then up to 10 matching actions, each naming its client and project. Indicators are a client's own, so they are given only when every project asked about is one client's.
- Each question and answer in such a chat records the projects its passages came from (`ai_messages.project_ids`); row-level security shows them only while the person can still see every one of those projects, the same rule as a project chat. A deleted project deletes them; the nightly job deletes them once a project they quote is past `chat_after_close_days` after closing, and the chat itself after `chat_idle_delete_days`.
- No case: "Ask the assistant" on a record still starts a chat in that record's project.
- At most 12 passages go to the model, as the AI service allows; a status question keeps the count first.

**Streaming.** `POST /api/assistant/query` with `Accept: application/x-ndjson` streams lines of JSON: `writing` once the search is done, `text` with the answer so far (firm staff only; a client person's answer is shown only after the client filter), then `done` with the saved answer, or `error`. Checks, the daily limit and the search run before the stream starts, so their refusals are ordinary error responses; the answer is saved in a second transaction as the same person. The AI service's `/v1/answer/stream` gives the model's reply as it comes, with half-written passage markers and name placeholders held back, and `wait` lines every 15 seconds while a reply that wasn't JSON is asked for again (so the web side's 2-minute idle timeout doesn't fire). A streamed answer that fails gives the question back to the daily limit (`app_uncount_ai_question`), as `ask()`'s rollback does, and is logged. If the person closes the card, the answer is still written and saved to the chat. Without that header the route answers as before, in one piece.

**Local model speed.** qwen3 writes a long hidden reasoning before every answer unless told not to: about 2,500 tokens, over 10 minutes for a five-word reply on a 4-core test machine. The AI service sends `think: false` and keeps models loaded for 30 minutes (`keep_alive`), so the same machine answers a short question in about 7 seconds (half a minute when the model first loads); a long answer across all clients still takes a minute or two, since it writes 2 to 6 tokens a second. The AI service logs how long the local model spent reading and writing each answer. The card says when the local model is answering, and the answer shows as it is written.

- **Title:** the first question on one line, cut at 60 characters, with no model call. The owner can rename it.
- **Case** (optional): the recommendation, action, finding, meeting or file the chat is about. The database checks it is a record of the same project that the person can see. "Ask the assistant" on an action, a meeting, a recommendation or a file starts a chat already linked to it, in the assistant card (a link to `/assistant?project=…&case=action:…` or `/assistant?chat=…` opens the card the same way). Deleting the record unlinks the chat; the chat stays in its project.
- **Who reads it:** only its owner, and only while they can still see the project. A consultant taken off a client loses the chat and its messages at once (the messages are hidden with the chat, not only the chat itself). Staffed again, they get them back, until retention deletes them. The same goes for a chat about a file or meeting its owner is later left out of (who sees an item), or with an answer citing one: hidden, not deleted, back if the item is opened up again (migration `0095`).
- **Sources shown again:** opening an old chat checks each citation again. A source the person can no longer open shows as "Source no longer available to you", without its title; a file with a newer version says so.
- **Where:** a floating card (`src/components/assistant/`), opened from the sidebar like the Files card and kept open across pages. Small, it shows the chats or one chat (a button switches back to the list, "+" starts a new chat); focused, it moves to the middle of the screen, grows, and shows the chats beside the open chat. `/assistant` stays as the landing for links. The client admin's consent view is `/assistant/consent` ("Assistant consent" in the user menu, page audit row 15): the sidebar's Assistant row shows as soon as the firm offers it and opens that view until the assistant is on for the admin; `/assistant` sends the admin there too.
- **API:** `GET /api/assistant/context?locale=&project=&case=` (the projects the person may ask about, the case's label, a client's questions today, and whether the model is local), `GET /api/assistant/conversations[?archived=1]`, `GET /api/assistant/conversations/:id?lang=`, `PATCH` (title, keep, archived), `DELETE`. `POST /api/assistant/query` takes `projectId` (null for all), and `caseType` and `caseId` when it starts a chat in a project.

## Two languages in one chat

The screen's own words change language at once, with no model call. A new answer is written straight in the screen's language. Only answers written before a switch need translating:

- An answer in the screen's language is shown as it is.
- One with a kept translation (`content_translations`, keyed by the answer's hash) is shown translated at once; `GET …/conversations/:id?lang=` returns it with no model call.
- The latest answer translates by itself (one call).
- Older ones fold into a one-line stub ("Answer in Arabic · translate") and translate when clicked. Then they are kept.
- Translations are labelled "Machine translated", with "Show original". The person's own questions stay as they wrote them.

So a switch costs one model call, not one per message.

## Retention

Chats quote client files, so they are kept only while needed (PDPL: keep personal data only as long as its purpose needs it). Text is small, so this is about privacy, not disk space. `npm run job:purge-chats` runs nightly as the schema owner (`app_purge_chats`):

- **Archive** after `chat_archive_days` (30) without a message, unless the owner keeps the chat. An archived chat is hidden from the list, opens read-only and comes back with a new message.
- **Delete** at the earlier of `chat_after_close_days` (90) after the project closes and `chat_idle_delete_days` (180) after the last message. "Keep" never stops this. Messages and their translations go with the chat; the audit log records the deletion (`assistant.chat_deleted`, reason `retention`), never what the chat said.
- The chat header shows the deletion date (`app_chat_delete_on`), and warns in the last 7 days. The owner can delete a chat at any time.
- Selah has no contract dates, so "the end of the engagement" is the project closing: the firm admin closes or reopens it from the project's handover card (`PATCH /api/projects/:id/state`), and the database sets `projects.closed_at`.

The firm should confirm the numbers with its own legal adviser before real client data is used.

## Masking names before a hosted model

When the model runs outside our server (`LLM_PROVIDER=openai_compat`, for example GPT-OSS on Ollama's cloud), the web app replaces known names with placeholders before anything leaves, and puts the names back in what comes back (`AI_MASKING=auto`, the default; `on` and `off` force it). People always see real names; only the model sees placeholders.

- **Closed by default (phase 3, R1).** The web app and the AI service each have an `LLM_PROVIDER`, and a hand-made `.env.local` can disagree with the service's. So under `auto` the web app asks the service each time (`GET /v1/model`, with the service token; `modelIsLocal()` in `src/services/ai-client.ts`), and leaves names unmasked only when the service answers `local: true`, which it does only when its own `LLM_PROVIDER=ollama` is given explicitly, the model is not one of Ollama's cloud models (a name ending in `-cloud` or `:cloud`, which the daemon forwards to ollama.com), and `OLLAMA_URL` points at this machine (`localhost`, `127.0.0.1`, `::1`) or the compose service `ollama` (`draft_locally()`, the same check as the org chart draft). The routes ask before their transaction opens (`prepare` in `route()`), so the check never holds the question counter's lock. The security page (`/legal/security`) and the assistant card say "local" only on the same answer. A hosted model, no setting, an error, a timeout or an older service without the route: masked. When the web app's own setting says hosted, it masks without asking. `maskingOn()` in `src/services/masking.ts`; proven by `tests/masking-on.test.ts` and `tests/db/assistant-chats.test.ts`.

- **What is masked:** the project's client and the firm (name, Arabic name, alias, short names), their people and the client's contacts (full names, the optional name in the other language, and name parts of 4+ letters), client people named only as an action's owner, people typed by name into a position of the client's organisation structure (current or past, migration 0091) or planned for its draft (migration 0098; the whole list gives these to the draft's editors only), the client's departments, and, for firm staff, the names of the firm's other clients (the project's names, `app_mask_names()`, for a project the caller can see), main Saudi cities, email addresses and phone numbers. Longest name first; Latin names as whole words; Arabic names also after a prefix such as و or ل, with short vowels ignored. All the names of one record share one placeholder (baseline: Assistant chats), so "Al-Nukhba Holding" and "شركة النخبة القابضة" are both `[ORG_1]`; before that the model took them for two companies.
- **Names in two languages (baseline: Name variants).** A person or client contact can have a name in the other language (`name_alt`, set by the admins who may change their address, logged, cleared on erasure), and a client up to 6 short names ("Al-Nukhba", "النخبة"), set by the firm admin on the client page. Latin names match however they are written: "Al Harbi", "Al-Harbi", "Alharbi" and "el-Harbi" are one name, and "Al-Harbi" also covers "Harbi" alone.
- **Other clients.** A consultant who types another client's name into a question has it masked too. Firm staff already see every client's name (they may ask to join a client), so the list shows them nothing new; other clients' people are not in it, and a client's own people never get other clients' names.
- **Where:** the question, every passage and record, the chat history, translations and file summaries. Embeddings are made locally and don't leave the server.
- **Built from the text, for everyone.** The assistant and translation mask with every name of the project written in what is sent (`app_mask_terms_in()` over the question, the passages, their labels and the history; `textMasker()` in `src/services/masking.ts`), never with the list of names the asker may read (`app_mask_terms()`, which leaves out the holder names a client manager may not read). So a name is masked whoever asks, and an answer is unmasked only to the names that were in the text sent. File summaries (firm staff only) use the project's list.
- **When:** at the moment of sending, from the current names, so a person or department added later is masked without re-indexing. The mapping lives only in that request.
- **Proven by** `tests/db/assistant-chats.test.ts`: no known name reaches the model's payload, and placeholders in the answer come back as the names.

Limits, to state plainly in the report:

- It reduces what leaves; it doesn't guarantee anonymity. A name that isn't in Selah (a person mentioned only inside a file) is not masked, and unusual details can still identify a client.
- A spelling Selah doesn't hold is not matched: someone registered as "ريم الحربي" with no English name is not masked where a file writes "Reem Al-Harbi". The admin adds the second name on the Team page.
- Another client's people, typed into a question, are sent as typed (nothing of that client is retrieved).
- Under PDPL, pseudonymised data can still be personal data. Sending it abroad still needs the firm's approval.
- The real fix is a model that runs on our server or is hosted in Saudi Arabia. The service already supports a local Ollama model; masking turns off by itself when the AI service says it is used.

## File summaries

`POST /api/documents/:id/summary` with `lang`. Firm staff only, like the assistant. `GET /api/documents/:id/summary?lang=` returns the kept summary, if any, and the file's text status, without calling the model.

Screen: the files on the project's Requests and files tab have a Summary button on each file available to the assistant (firm staff). It shows the kept summary in either language, each line with page links that open the file at that page; when there is none, a Summarise button makes it. A file whose text can't be read is marked "Text not readable".

- Made once per file version (its SHA-256) and language, from the file's indexed pages, then kept for everyone who can open the file.
- Every line cites the pages it rests on. Lines citing pages the file doesn't have are dropped; a summary with no line left is refused.
- Read with the file's own rights. Deleted when the AI flag goes off, the visibility or department changes, the file is archived, or a new version is uploaded.
- At most 30 new summaries per person an hour (translations allow 200).
- When the model fails on a file, or gives no line that cites it, that file and language aren't sent again for 10 minutes (per server process), since failed calls don't count towards the hourly limit.
- A file that isn't indexed yet, or has no readable text, is refused.

## Drafting a structure from pasted text

Org chart, part 4 ([import-export.md](import-export.md), "Importing an organisation structure"). On the structure import page the firm's editors may "Paste a list or description and let the assistant draft it": a job list, an outline, text copied from the firm's slide. `POST /api/clients/:id/structure/import/draft` (`draftFromText()` in `src/services/org-chart-import.ts`):

- **Only with the local model** (the coordinator's decision, 18 Nov 2026). A pasted chart is mostly names of people Selah does not know yet, which masking cannot catch, so the option exists only while the model runs on Selah's own server. Two independent checks, both closed by default: the web app offers it only when its own `LLM_PROVIDER` is `ollama`, given in so many words (`localModel()`; unset or any other value counts as hosted, and `apps/web/.env.example` sets it with a comment), and the AI service drafts only when **its** `LLM_PROVIDER` is `ollama`, given explicitly, with a model that is not an Ollama cloud model and an `OLLAMA_URL` on this machine or the compose service (`draft_locally()`; otherwise a 409 "local model only" before the model is asked, which the screen words as "the assistant can't draft here"). The two settings can disagree (the hot-reload setup reads the root `.env` for the service and `apps/web/.env.local` for the app); the service's refusal holds whatever the web app believes.
- **Only where the assistant is on.** The way the assistant decides it: `authorize()` gives the reader `assistant.query` on at least one of the client's projects they can open (`assistantProjects()`). Otherwise (a client with no project yet, say) the paste option is hidden and the call answers Not found. Only the draft's editors reach it at all.
- **It never handles people.** The schema has no field for a person and the prompt asks for units and positions only, never a person's name, even one the text gives. The screen asks for titles only: "Write titles only and leave people's names out: names are added later" (through the Excel template's holder column, or on the Structure tab). Whatever else comes back from the service is dropped (`draftOrgChart()` keeps only the schema's fields, and `draftRows()` reads none for a person).
- **Masked as a second line.** The text still goes through `textMasker()` with those projects, the same masking as the assistant's: every name of the client's projects written in it (the client and the firm, their people, the client's contacts and departments, people typed into its structure or planned for its draft, other clients' names for firm staff), e-mail addresses, phone numbers and main Saudi cities become placeholders. Placeholders come back only where the text had them; one the text never had stays a placeholder and is dropped.
- **One call to `chat_json` with a strict schema** (`POST /v1/org-chart/draft` on the AI service: `ORG_DRAFT_SYSTEM` and `ORG_DRAFT_SCHEMA` in `services/ai/app/prompt.py`, every object closed with all its fields required). The prompt says to use only what the text says, copy titles exactly, never add a unit, position or specialty, never write a person's name, and never suggest, improve or judge the structure. The service checks the reply's shape only (`check_org_draft`): fields of the right type, at most 300 units and 600 positions, 300 characters a field; a reply that is not that object is a 502, and the page says the assistant could not draft rows.
- **It never adds.** `draftRows()` in `src/lib/org-chart-import.ts` keeps a unit or a position only when the text writes it, and each mention carries one unit or one position at most; in a unit, one position per title, unless the text lists the title separately more than once (one per line or item, "- Accountant / - Accountant"), so a second mention inside a sentence ("reports to the Finance Manager") never makes a second position; a specialty must be in the text too. Anything else is left out and listed on the review step under "Left out: not in your text", never added. A code is kept only when the text writes it. A position whose unit is not in the text has no unit, for the person to place.
- **The same review step.** The rows land in the review step of a file import, checked by the same code, and are saved only by "Save to draft"; nothing is published.
- At most 20 drafts per person an hour, 20,000 characters each, counted again after masking (the AI service takes as much, and a placeholder can be longer than the name it hides: «جدة» is `[PLACE_1]`); a text too long either way is refused before anything is sent, and the screen says by how many characters to shorten it, also for a paste far over the limit (the route takes up to ten times the limit so the server can count, `ORG_DRAFT_BODY`). Audited as `org_chart.import_draft` with the text's length and hash, how many names were masked, the rows kept and left out, and the model: never the text.
- **Proven by** `tests/db/org-chart-import.test.ts` with a fake model: with a hosted model (or a setting it cannot read) the option is off and nothing is sent; the text the local model receives holds no known name, e-mail or phone number; no row names anyone even when the model answers with people; a position the text never had is left out and listed; the call is refused where the assistant is off. `tests/org-chart-import.test.ts` covers `draftRows()`, and `services/ai/tests/test_service.py` the endpoint's schema (no field for a person) and checks.

Reading a picture of a chart is not built: the AI service is text-only, and names inside an image cannot be masked before a hosted model sees them.

## Meeting summary sources

Each line of a meeting summary can point at where it came from (`meeting_summary_sources`):

- a passage of the meeting's transcript (character range), seen by the firm only, as the transcript is;
- or a page of a file in the same project, seen by whoever can open the file. The file's version is stamped.

Only the firm adds them. Rewriting the summary's text drops its pointers, since the lines have moved.

- `POST /api/meetings/:id/summary/sources` with `line` and either `kind: "transcript"` and `quote` (the passage copied from the transcript; the server finds its place) or `kind: "document"`, `documentId` and `page`.
- `DELETE /api/meeting-summary-sources/:id`.
- The meeting page lists each line's sources under the summary: a transcript passage opens its text (firm only), a file page opens the file at that page, marked when a newer version of the file has been uploaded since. Firm staff who run a held meeting link and remove them there.

## The client assistant

Wave 3 (F39) gives a client's admins and managers the same assistant, read-only, behind four locks. Action owners never get it: they read only their own actions (row-level security too, since decision 1b and migration `0081_owner_actions`) and the files shared with them or filed under their department, and the index has no per-person filter yet. `app_set_client_ai()` refuses the role, and a passage of an action is read only while the action itself can be read (`with_source`).

1. **The firm admin offers it** on the client page ("Client assistant" card): on or off, which roles (client admin, client manager), and how many questions a person may ask a day (1 to 200, default 20). `app_set_client_ai()` takes it only from the firm admin, only for an active client whose people sign in with full records (not a pitch, not consultant-managed, not minimal records). The client's admins are told.
2. **The client's admin agrees** on `/assistant/consent`, after reading a notice (in their language) of what it reads, what it never reads, that it gives no rulings, how chats are kept, and who can use it. `app_consent_client_ai()` records who, when, the notice version (`CLIENT_AI_VERSION`, the same date as `app_client_ai_version()`) and the language. The firm admins and the lead are told. The same view then shows what was agreed, by whom and when, who can use it and the daily limit, with the switch to withdraw: the admin can switch it off at any time (`app_withdraw_client_ai()`); the firm admin switching it off, or offering it to a role it didn't cover, ends the consent too, so the admin agrees to what is actually on. A new notice version needs a new consent.
3. **The database decides each request.** `app_client_ai_on()` is true only while all of the above holds for the caller's role and client. It sits in `Principal.clientAssistant`, which `authorize()` checks for `assistant.query`, and in two RESTRICTIVE policies: on `ai_chunks` (a client reads passages only while it is on, and only of files, recommendations and actions; never review notes, meetings or anything else) and on `ai_conversations` (the chats hide when it is switched off and come back when it is on again). Every other policy still applies, so a client reads only passages of records it can already open: no firm-only or other people's private files, assessment scores, firm notes, lessons, pitch material, closing-survey answers or audit data are indexed for them at all.
4. **Every answer is filtered before it is shown or stored.** The AI service gets `audience: "client"` and extra rules (`CLIENT_RULES` in `services/ai/app/prompt.py`): facts only, no legal or compliance rulings (the facts the passages give instead), no rating of the work, no drafts except a facts-only progress update, no guesses about the firm's intentions or internal views, no other clients, refer decisions to the consultant. Then `clientAnswerProblem()` (`src/lib/client-ai.ts`, Arabic and English patterns) and `app_names_other_client()` check the answer; a hit replaces it with a fixed refusal in the asker's language, or with "can't confirm" when it named another client. The audit entry records which passages were sent and why an answer was filtered.

**What a client person may ask for, beyond finding and explaining (Gate B, 19 Nov 2026).** The four open questions of the phase 3 assessment were answered:

- **"Who is my consultant?"** `consultantIntent` (`src/lib/assistant-search.ts`) notices the question as such, in both languages ("who is my consultant?", "who do I contact at the firm?", «من مستشاري؟», «مين يتابعنا من المكتب؟»), not every question that names a consultant ("what evidence does the consultant accept?"). `consultantRecords` then adds one record per client project asked about (at most 3): the client's lead and deputy and the consultants staffed on the project (not observers), the same people Help and the project's People tab show (`projectConsultants`, `app_my_consultants()`), read as the asker and only for a project they can see (`app_can_see_project`). Names only, never e-mail addresses; cited as the project's record. The record does not take a file passage's place. A firm person gets no such record. With masking on, the names go to the model masked like any other.
- **"My deadlines"** (client people only; firm staff get the project's status as before). When a status question says it is about the person's own work ("my", "mine", "assigned to me", «المطلوب مني», «عليّ», «مهامي», «إجراءاتي», «مواعيدي»), `mineIntent` is true and `statusRecords` keeps only the actions the person owns, or is named on as the typed owner (no account) with their own name. Not "my company", "my team", "my manager's", "my CFO", "my direct reports", "Ahmed's deadlines, not my own", nor «علي» without its shadda (a name). "My deadlines" with no status word reads every open action of theirs. The filter is added to every query of `statusRecords`, under the same row-level security, so it only ever narrows; the search's own records (a recommendation lists all its actions) are left out of such a question. The count says "your actions", and the model is told to call them that.
- **Legal questions.** Still no ruling (the `CLIENT_RULES` rule and `clientAnswerProblem()`), but no bare refusal either: the model is told to give what the relevant passages state, each point cited, and to end by saying that whether it is enough is for the consultant or a legal adviser. The filter reads the text folded to one spelling first (`foldArabic`, `src/lib/arabic-fold.ts`: no marks, nunation or tatweel, one alef, ى → ي, ة → ه), and catches a verdict whatever its subject: compliant, in breach, lawful, legally sufficient, meets / satisfies / is in line with / conforms to the law or the regulations, and in Arabic «ممتثلة للنظام», «متوافقة مع اللوائح», «مطابقة للائحة», «كافية نظامًا», «ملزمة نظامًا», «تحقق المتطلبات النظامية», «مخالفة للائحة», «السياسة نظامية». What a rule requires is a fact and stays ("disclosure is legally required within 15 days", "directors must comply with the Companies Law", «يجب أن تستوفي...»). When an answer still holds a ruling, `withoutRulings()` takes out those sentences (and list lines); what is left passes the whole client filter again and is shown with "This is what your sources say. Whether it is enough is for your consultant or a legal adviser to judge." When nothing is left, the fixed refusal is shown with the sources it cited still listed.
- **A progress-update draft** (the one draft a client person may get; firm staff get the same draft for the firm's report, see "The consultants' progress draft and the firm's report"). `progressDraftIntent` notices "draft my progress update", «اكتب مسودة تحديث التقدم» and close forms, but never a message, e-mail, letter or anything written to someone or asking for something ("to the consultant", "to the CMA", «إلى المستشار», «تطلب»). Any other draft (`otherDraftIntent`: an e-mail, a letter, a decision, minutes, a policy) is refused in code, without asking the model, with a fixed answer that offers the progress update instead. `progressRecords` gives the model the actions the person can read (row-level security: a manager, their departments'; never a draft action, D6): a count of done (verified), closed without full verification (each with its reason: partly implemented, risk accepted, not applicable, superseded; never called done), in progress, waiting for the firm's review, waiting on the company, and late, then up to 9 actions with their dates. The draft is built only from those, each point cited, and always starts with "Draft: check before sending" / «مسودة: راجعها قبل الإرسال», once: the AI service and the web app read the same forms of the mark (`DRAFT_MARK` in `services/ai/app/prompt.py`, `withDraftMark` in `src/lib/client-ai.ts`) and keep the one canonical line. An answer the client filter changed (a legal refusal) gets no mark. Selah never sends it, shares it or files it as a record: it is an answer in the person's own chat, like any other, kept and deleted with the chat. No rating words, in the draft only (`progress_draft` on the AI request): the AI service takes out every sentence of the draft that rates the work ("good progress", "on track", "great work", "progressing nicely", "on target", «تقدم جيد», «العمل جيد», «على المسار الصحيح», «وفق الخطة», «إنجاز كبير» and more: `RATING_WORDS` and `without_ratings()`), reading the folded spelling and never words in quotation marks (a policy may say "excellent"). "Late", "overdue", "outstanding" (still open) and "on schedule for 3 May" are facts and stay. A draft left with nothing but the mark is "can't confirm". Other client answers are not changed by this check.

Proven by `tests/db/client-assistant-gaps.test.ts` (a department-limited manager gets only their department's people and deadlines, "mine" only narrows and is the client's only, another client gets nothing, the draft's records, closed actions and mark, another draft refused without the model, file passages kept beside the consultant record, the new records masked, the legal facts), `tests/client-assistant-gaps.test.ts` and `tests/legal-rulings.test.ts` (the question words, every ruling phrasing of the review and the facts that stay, `withoutRulings`, the mark) and `services/ai/tests/test_service.py` (the client rules, the rating-word check and the facts it keeps). In the client eval, every legal question (J1 to J7) also checks that no ruling is in the answer, with a wider word list of the eval's own.
Each question counts toward the person's daily limit (`app_count_ai_question()`, firm day; staff are counted but not limited); over it the page says so. File summaries stay with firm staff (`document.summarize`). Chats follow the same retention as staff chats.

`tests/db/client-assistant.test.ts` covers the switch, consent, roles, withdrawal, ineligible clients, hidden chats, the limit, the filter, the other-client check, version parity, and leak probes per role: canary passages are planted in the firm's own file on the client's project, another person's private file, an archived file, a file not open to the assistant, another client's file, a firm-only meeting note and a review passage. Each client role searches for them through the real scope and a forged one, and none comes back; a department's file stays in its department, and the model's request is checked to carry none of them.

## The consultants' progress draft and the firm's report

Fahad, 19 Nov 2026 ("firm's report only"; migration 0110). Firm staff get the client's facts-only progress draft, reused rather than copied: the same `progressDraftIntent` and `otherDraftIntent`, the same `progressRecords`, the same mark (`withDraftMark`) and the same rating-word check in the AI service (`check_answer` now strips ratings from any progress draft, staff or client).

- **What it reads: the progress records only** (review B1 and B2). The draft becomes the note of a report every client reader sees, whatever their department, so it is built only from `progressRecords(..., { clientSide: true })`: released actions under shared recommendations (the same work `app_project_progress(client_side)` counts for a report) and, at a client with departments on, only work tagged to no department, neither the action nor its recommendation (actions have no audience picker). Nothing else goes to the model with it: no file passage, no searched recommendation or action, no chat-subject record (a chat about a firm-only recommendation gives no special passage), no indicator and no earlier turn of the chat.
- **The prompt.** `STAFF_DRAFT_RULES` (`services/ai/app/prompt.py`), added only when `progress_draft` is set for staff: facts only (done, in progress, waiting, late, each with its date and citation), the mark first, no rating words, nothing about the firm's intentions or internal material, written to the client's people.
- **Other drafts as before.** Firm staff drafting anything else (a follow-up message, minutes) is unchanged: an ordinary answer from the sources. Only a client person's other drafts are refused in code (review S3).
- **Kept as a draft.** The answer is stored with `ai_messages.progress_draft`, so the chat knows it is one. Like any answer, it lives only in the asker's chat and is deleted with it.
- **"Use as draft"** (under a staff draft on one client project; not in a chat across projects). `/assistant/draft/<message>` reads the draft (`draftForReport()`: the asker's own answer, a client project they may write reports for) and opens the firm's report page with its text, without the mark, as the note: this month's status pack when it still waits for its note (the Issue dialog opens filled in), else the project's Progress tab with **New report** open and filled in. It reads only; nothing is saved until the person presses Create report or Issue there, and the chat keeps only its answer. The report then remembers the answer it started from (`reports.draft_message_id`: the writer's own draft only, checked by the database).
- **"Send to the client"** under the same draft opens the report page's own Send dialog (`ReportSendDialog`) for the report made from that draft (`reportFromMessage()`), or says there is none yet. Opening it only reads. It never sends by itself and never skips the approval: the report is sent only when a person presses Send in the dialog (`{ confirmed: true }`), and only once a firm person other than its writer approved it (the client's lead or deputy consultant, an internal project's lead, or the firm admin; `docs/rules.md`). No job or model call sends a report.
- **The client's draft stays an answer in their chat**; a client page to keep and edit their own report is a later improvement (`docs/progress-checklist.md`, LI08).
- **For a later builder (report templates).** A template fills the same note field on the same page; `draftForReport()` in `src/services/report-send.ts` is where a chosen template would be put together with the draft, and the New report and Issue dialogs already take a pre-filled note (`FormDialog` `defaultOpen`, `notice`, `extra`).

Proven by `tests/db/report-send.test.ts` (the draft's records leave out firm-only work, the mark and the stored flag, nothing but the progress records reaching the model (a firm-only chat subject, a firm-private file, firm-only searched records and an earlier turn all kept out), other staff drafts unchanged, "Use as draft" saves nothing and only reads the asker's own draft, approval required, the writer never approves, a client never sees an unapproved report, the Send dialog only reads and the send needs the confirmation), `tests/report-send-ui.test.ts` and `services/ai/tests/test_service.py` (the staff rules, the rating words taken out of a staff draft, streamed or not).
