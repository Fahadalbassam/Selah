The helper's body is the old method's body line for line: one first call, one retry only when `json_object` finds nothing, retry messages = original system + user + `{"assistant": raw}` + `RETRY_JSON`, returns the found object or else the **first** raw reply, and lets exceptions from `_complete` (HTTP status, JSON decode) through as before. A probe with two `content: null` replies gives `''` after exactly 2 calls, roles `system, user, assistant, user`. The retry sends the hosted model nothing it wasn't already sent: its own reply plus the fixed retry line. No `num_ctx` or other Ollama option goes into the hosted body.
- **Ollama request body.** `options.num_ctx` (`llm.py:59`) is where Ollama's `/api/chat` expects model parameters. `think`, `keep_alive`, `format` stay at the top level, as before. Both streamed and plain calls go through `_chat`, so both send it.
- **Streamed path.** `chat_json_stream` only gained `_check_context(event)` on the `done` event (`llm.py:96`). Pieces, the info log and errors are unchanged. The test covers the stream warning.

## Should-fix

1. **The overflow warning misses the retry case, which is where passages can disappear without notice.** `llm.py:199` resends `[system, user, assistant(raw), user(RETRY_JSON)]` to Ollama. When those messages are longer than `num_ctx`, Ollama's chat prompt builder drops the oldest messages that don't fit. It keeps the system message and the last ones, so the dropped message is the **user message that holds the passages**. The model then answers from the rules, its own bad reply and "reply again". `prompt_eval_count` is well under `num_ctx` in that case, so `_check_context` stays silent. The retry prompt is always longer than the first one, and the usual reason a format-constrained local reply isn't JSON is that it was cut off, so this path is the likely one in a long prompt. Fix: on the Ollama retry, skip it (or log a warning) when the first call's `prompt_eval_count + eval_count` was near `num_ctx`. Or send the retry as a fresh `[system, user + RETRY_JSON]` without the old reply.
2. **The threshold only counts the prompt, not the reply, and it misses prompt-cache hits.** `llm.py:65` warns only when `prompt_eval_count >= num_ctx`. (a) A prompt of 16,000 of 16,384 tokens leaves about 380 tokens for the answer. Ollama then shifts the context while it writes, which silently drops the start of the prompt or cuts the JSON short. There is no warning. (b) `prompt_eval_count` counts only tokens Ollama had to evaluate. A prefix reused from the loaded cache (same system prompt; always on the retry) is not counted, so a truncated prompt can report less than `num_ctx`. Fix: warn on `prompt_eval_count + eval_count >= num_ctx`, or on the prompt reaching about 90% of it. The test at `services/ai/tests/test_service.py:560-570` should then move with it.
3. **The streamed answer's comment is now wrong, and the worst case is longer.** `services/ai/app/main.py:210` says the asking again "for a hosted model includes its own retry". It now does for the local model too. So a non-JSON streamed local answer can cost up to three full local runs (stream, then `chat_json`, then its retry). On today's CPU-only server, a full answer is 1 to 3 minutes (`docs/review/section-7-model-retrieval-redaction.md:16`), and each non-stream call may take up to `request_timeout_s` = 120 s. That makes about 3 + 2 + 2 = 7 minutes, still under the web's `STREAM_TOTAL_MS` = 600 s (`apps/web/src/services/ai-client.ts:60`) but close, and Ollama serves one person at a time. Fix: update the comment. Consider having the stream fallback call a single `_complete` and not `chat_json`, so the local model runs at most twice.

## Note

4. **Non-stream local calls can outlive the web's timeout.** The web's `call()` aborts after 60 s (`apps/web/src/services/ai-client.ts:8`). On the CPU server, translate, summarize and org draft with a slow first try now start a second local run. That run keeps the single local model busy after the web has already given up (uvicorn doesn't cancel the handler, httpx waits up to 120 s), so the next person's question waits behind it. Before this change, a non-JSON reply failed at once with a 502.
5. **16,384 is below what the service accepts.** 12 passages × 4,000 characters + a 2,000-character question + 8 history turns (`main.py:73`, `config.py:31-33`) is up to about 50k characters. In Arabic that can be more than 16k tokens. Summarize accepts 200 pages × 20,000 characters (`main.py:91-95`). So the warning can fire on valid requests that are as large as allowed. Say so in the `.env.example` comment, or cap the passage count to the context. At 16k context the qwen3:4b cache is about 2.3 GB of RAM (36 layers × 8 KV heads × 128 × 2 × fp16). That fits the 16 GB server, but there is no upper bound (`config.py:27` only has `ge=2048`), so `LLM_NUM_CTX=262144` would be accepted and exhaust RAM. Consider `le=131072` or similar.
6. **A bad `LLM_NUM_CTX` fails late.** Settings are read lazily per request (`config.py:36-38`, `main.py:45`), and `/health` (`main.py:139`) doesn't read them. With `LLM_NUM_CTX=abc`, or with an empty value when run outside compose, the container reports healthy and every AI request returns 500. This is the same for every setting, so it isn't caused by this branch, but the branch adds one more way to break it. Calling `get_settings()` at import or startup would fail fast.
7. **Weak test.** `test_both_providers_share_one_json_fallback` (`tests/test_service.py:631-636`) greps the source text of `chat_json`. It passes even if the call result is ignored, and breaks on a harmless rename. The retry tests that do call it already cover the behaviour, so this test can go. No test asserts that the hosted body carries no `num_ctx` (true by probe).
8. **`json_object` now unwraps arrays for the local model as well.** A reply of `[{"a":1}]` returns `{"a":1}`, the inner object, because of `find("{")` / `rfind("}")`. This was already true on the hosted path. It's harmless with the strict schemas, but it's a new behaviour for Ollama.
9. **Wording.**
   - `config.py:18-19` has one line well past the file's wrap width ("...than a GTX 1050 has). "openai_compat" calls any hosted API that").
   - README says Pascal cards "also need Ollama's CUDA 12 build". The compose file pins `ollama/ollama:0.40.6`, and whether that image picks the CUDA 12 libraries by itself was not checked here. If it does, the sentence suggests a manual step that isn't needed. Check it, or reword it to "need Ollama's CUDA 12 libraries (newer CUDA drops Pascal)".
   - The 1050 Ti has 4 GB. The old text probably meant that card, so the new wording, "2 GB, or 3 GB on one variant", is correct for the GTX 1050 itself.
