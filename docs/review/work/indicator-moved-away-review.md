## 2. Checked and found sound

**Who is told**
- `app_kpi_moved_away_audience` (`0120:50-61`) returns the client's lead and deputy (`client_assignments.is_lead OR is_deputy`) with an active firm membership, and the client's active `client_admin` members. Nobody else: no manager, action owner, observer, staffed consultant, firm admin who is not the lead, or another client's people.
- Everyone it returns can read every indicator of the client. `app_kpi_readable` (`0063:203-207`) gives the firm `app_firm_works_with`, which means firm admin or an assignment row (`0000_baseline.sql:4040-4044`, `:1450-1453`). It gives the client admin `app_dept_ok`, which is true for `client_admin` in any department (`0000_baseline.sql:4844-4851`). No later migration redefines these functions or adds a policy on `client_kpis`.
- One membership per user (`org_memberships.user_id` is unique, `src/db/schema/app.ts:182-185`), so "active at the firm" cannot be fooled by a second membership.
- Probes: a switched-off lead is not told, and an observer gets `app_kpi_tells_me` = false. Tests: the firm admin off the team, a staffed consultant, a switched-off admin, managers in both departments, an action owner, and the other client's lead and admin are not told (`tests/db/indicator-moved-away.test.ts:200-218`, `:326-360`).
- A deputy who steps down is not mailed (`:389-399`). Someone removed from the team can still open their old notice, but the line is read under their rights (`src/services/notifications.ts:120-160`), so it shows "gone" with no figures and no link.
- The notice names the indicator, its value, period, unit, baseline, direction, and the target and its date once passed. That is nothing a recipient cannot read on the indicator page. No recommendation or link is named, so the D6 drafts rule and the firm-only label do not come into it.
- The mail is the existing `follow_up.digest`: one line and a link, with no titles and no figures (`src/lib/mail-templates.ts:238-256`).
- The notice is not copied to the deputy a second time: `copy_lead_alert` only copies lead-alert kinds (`0054_pulse.sql:174-177`), and `indicator.moved_away` is not one.

**Every save path**
- Typed values (`addValue`, `src/services/indicators.ts:472-483`), files, sheets and system pushes (all through `saveBatch`, `src/services/indicator-data.ts:319-325`, one `INSERT` for the batch) insert into `client_kpi_values`. That is the only table the trigger is on.
- A value is never updated except for the firm's check (`0063:330-347`). No migration or script outside the tests disables triggers on this table (grep for `DISABLE TRIGGER` and `session_replication_role`).
- Corrections are inserts, and the `(kpi_id, period)` key with `ON CONFLICT DO NOTHING` keeps it to one notice per period: tests `:231-250`.
- A file with several months tells about the last month only: test `:315-323`, and probe B2.

**Migration, functions and grants**
- `app_queue_digests`: I diffed it against its latest earlier text (`0081_owner_actions.sql:143-186`). It adds one `WHEN` branch and two `AND NOT` clauses and keeps every earlier clause: the D6 line, the 1b line, the mutes, the 8-day window, `SKIP LOCKED`, the once-a-day check and `app_can_reset_password`. No migration from 0082 to 0089 redefines it (grep). It is still not `SECURITY DEFINER`, the same as in 0081.
- Constraints: `notifications.kind` has no CHECK, and none was added. `outbound_kind` is not touched (the existing `follow_up.digest` kind is reused); I listed it in the migrated database and it is intact.
- `SET search_path = public, pg_temp` is on all four functions. In the migrated database (probe): `app_kpi_wrong_side`, `app_kpi_moved_away_audience` and `app_queue_digests` cannot be executed by `selah_app`. `app_kpi_tells_me` can (it is needed by the page) and answers only about the caller. The trigger function errors if called directly.
- `kpi_moved_away_log` has row-level security on and no grant. As `selah_app`: `permission denied`.
- `mail_kpi_mutes` grants SELECT, INSERT and DELETE, with the policy `own` (`user_id = app_uid()`, and on insert `app_kpi_id_readable`). Probe: inserting another person's mute is refused by row-level security, deleting another person's mute deletes 0 rows, and UPDATE is refused.
- Schema and snapshot: `npx drizzle-kit check` says "Everything's fine", and a probe `drizzle-kit generate` says "No schema changes". `0120_snapshot.prevId` equals `0089_snapshot.id`. The journal `when` is later than 0089's. But see finding 8.
