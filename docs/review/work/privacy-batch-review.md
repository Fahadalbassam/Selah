## Should-fix

### S1. The confidential-request flow now dead-ends for a manager who did not upload the file
`0016_info_requests.sql:162` / `0106_classification_leaks.sql:255` (check_info_request_file) refuses to attach a file the assistant reads to a confidential item, with "turn the assistant off for this file first". The screen says the same (`messages/en.json` `infoRequests.assistantFile`: "Turn the assistant off for it before using it on a confidential item.", shown from `info-requests-tab.tsx:418`). After 0108 (`0108_privacy_batch.sql:14-25`, `services/documents.ts:204-206`), a client manager answering the item with a colleague's or the admin's file cannot switch it off. The service returns Not found, and the database refuses with "only the person who uploaded…". She is told to do something she is no longer allowed to do, and the screen does not say who can.
Concrete case: in the `privacy-batch.test.ts` fixtures, D.byAdmin (uploaded by cadmin, assistant on) cannot be switched off by mgrA (the test asserts this), so mgrA cannot attach it to a confidential item.
Fix options, product's call: (a) let anyone on the owning side switch the assistant *off* and keep *on* for the uploader or admin (the direction that reduces exposure); or (b) keep the rule and change the refusal and `assistantFile` text to name the uploader or the admin, as `AssistantWho` already does in the file menu. Also note that D1 covers switching off as well as on. That is a privacy-reducing restriction (a manager who sees a sensitive file with the assistant on cannot take it out), so it is worth confirming with the product owner that this was intended.

### S2. A cancellation still reaches a shut-out attendee who never got an invitation
`0108_privacy_batch.sql:95` (app_send_meeting_invites: `m.status = 'cancelled' OR NOT shut_out`) and `:113-118` (app_meeting_mail_ok: the shut-out filter applies only to `meeting.invite`). If an invitation from before the rule was never mailed (the meeting was booked without "send invites"), or a manager becomes shut out later (a new department is created, or she is taken out of one, so `app_user_sees_whole_project` turns false), cancelling the meeting mails her a `meeting.cancel`. That mail is an ICS carrying the meeting's title, time, link or location, and the attendee e-mails, for a meeting she cannot open and was never told of.
Probe 4: a meeting with mgrA attached and no invite ever sent, set to cancelled. `app_meeting_mail_ok(mid, 'mgrA@…', 'meeting.cancel')` returns **true**.
Fix: send the cancel to a shut-out attendee only when a `meeting.invite` to her address was actually sent (`sent_at IS NOT NULL`). That is the same test `meeting.removed` already uses at `:110-112`, and it gives the same answer in both functions.

## Notes

### N1. The stuck notice can be fired without a real transition, and twice per call site (low; adds nothing new)
`0108_privacy_batch.sql:139-146`. The guard is "a `status_changed → blocked` event by this caller at `now()`". `activity_events` lets any project reader INSERT with `actor_id = app_uid()` (`0000_baseline.sql:1633`). So on an action that is already blocked, anyone who sees it can insert that event and call `app_tell_firm_stuck` as often as they like. Nothing de-duplicates within one transaction.
Probe 2: A.fin already blocked; owner1 inserts the forged event and calls the function twice, in two transactions. Result: lead, deputy and staff each have **4** `action.blocked` notices. Recipients are still only people who may read the action, so nothing leaks. The `notify` policy (`0000_baseline.sql:1642`) already lets `selah_app` insert notifications for anyone the caller can see, so this is not a new capability. It does leave a forged "marked stuck" row in the project history, though that was already possible.
If wanted: add `AND NOT EXISTS (notifications kind='action.blocked' AND entity_id=act AND created_at=now())` for de-duplication. Or move the notice into an `AFTER UPDATE OF status ON actions` trigger (`WHEN NEW.status='blocked' AND OLD.status<>'blocked'`). That ties it to the real transition and makes the public function unnecessary.

### N2. "Uploader of that version" can be reached by uploading a new version (by design, but say so)
`services/documents.ts:224-265`. Any manager on the owning side may upload v2 (`newVersion` needs only `document.manage`). She then becomes v2's uploader and owns its switch. She can re-upload v1's bytes as v2 and switch the assistant on, even though v1's uploader or the admin chose to keep it off. A direct-SQL copy is stopped (probes 1/1b/1e: `documents_storage_key_unique`; probe 1c: `uploaded_by` is frozen, "a stored file cannot change"). The service path is consistent with the stated rule. It is still worth one line in `docs/rules.md` so nobody treats D1 as a hard guarantee. The INSERT of a new version is not covered by `document_manage_assistant` (UPDATE only). Today that is fine because the service copies `old.aiIndexable`, but a direct-SQL v2 may carry a flag different from v1.

### N3. Database and policy disagree for action owners (existing gap, now narrower)
`check_document_assistant` lets any uploader on the owning side switch (`OLD.uploaded_by = app_uid()`), including an `action_owner`. `document.assistant` and `document.manage` in `policy.ts:240-245` have no `action_owner` grant, and `check_document_manage` checks only the owning org. So an action owner can switch her own upload by direct SQL but is never offered it. This was looser before 0108 (any action owner, any client file). Harmless, but if the product rule is "never for action owners", add `app_role() <> 'action_owner'`.

### N4. `cannotOpen` tells every reader of the meeting which colleagues have department limits
`services/meetings.ts:327-334`, `app_meeting_shut_out` (`0108:73-83`, granted to `selah_app`). Probe 3: an action owner invited to the meeting gets mgrA's id back. That is the intended UI ("Can't open this meeting"). It does mean an action owner or a client manager learns that a named colleague is department-limited. That fact is probably visible elsewhere already (the people page, or the warning shown before booking), so it is fine if accepted.

### N5. A contact with the manager's e-mail still gets the invite
`app_send_meeting_invites` and `app_meeting_mail_ok` match contacts by address with no shut-out test (`0108:97-98`, `:114-116`). If the firm keeps a client contact with the same e-mail as a department-limited manager and invites the contact, she gets the full invite. This needs a deliberate firm action and predates 0108 (the same gap exists for audience "except" lists in 0095), so it is a note.

### N6. Small things
- `blockHintFirm` (`messages/en.json:1068`) names "the client's lead consultant, their deputy" on internal projects too, which have no client. Only staffed consultants are told there (`0108:157`, `p.kind = 'client'`).
- `refuseShutOut` (`services/meetings.ts:221-228`) passes anyone not in `app_meeting_invitees` for the caller, for example a client manager booking who cannot list a colleague. The database trigger catches it, and `meetingError` maps the message to `invitedLimited`, so the user sees the same text. Fine.
- The ICS that goes to the other attendees and the `.ics` download still list a shut-out attendee's e-mail. They include her name and address only, which is acceptable.

## Things probed that held

- **Assistant flag, every write path.** There is one route (`api/documents/[id]/assistant`) and one service write (`setAssistantFlag`), and it asserts `document.manage` and then `document.assistant`. First uploads never set the flag. The only `ai_indexable` writes inside the database are switch-offs in owner-run definers: `retire_old_version` (0005), `app_withdraw_document` (0018/0106), and `app_retire_confidential_versions` (0106, not granted). No trigger assigns `NEW.ai_indexable`. Jobs and scripts do not write the flag. The `current_user = 'selah_app' AND app_uid() IS NOT NULL` guard lets the #193 one-off switch-off, purges, migrations and indexing through. `INSERT … ON CONFLICT DO UPDATE SET ai_indexable` still fires the column trigger. Trigger order is `confidential_file`, `document_manage`, `document_manage_assistant`, as the comment intends. `check_document_assistant` is not SECURITY DEFINER on purpose (it reads `current_user`, like `check_document_rename` in 0106). `pg_temp` functions are never resolved for unqualified calls, so the missing `SET search_path` is not exploitable, and `selah_app` cannot create objects in `public`.
- **Attendee paths.** `bookMeeting`, `addAttendee` and a direct INSERT are all refused. The meeting's department can never change (`meeting_department`, 0021: "a meeting keeps its department"), so a department meeting cannot be turned into a whole-project one. `check_attendee` refuses any change to an attendee's `meeting_id`, `user_id` or `contact_id` (baseline 4325). There is no rebook, recurring or agenda-to-meeting path that inserts attendees (`insert(meetingAttendees)` appears only in `services/meetings.ts`). Action owners pass, as intended. A queued invite from before the rule is withdrawn at send time by `app_meeting_mail_ok`. `meeting.removed` is unchanged.
- **Stuck notice recipients.** It is SECURITY DEFINER with `search_path = public, pg_temp`, `REVOKE … FROM PUBLIC`, and granted only to `selah_app`. Recipients are joined to an *active* firm membership with role `firm_admin` or `consultant`, so client-side project members are excluded. Observers are excluded, and the database already forbids a lead or deputy being an observer (0051). A `user_private` recommendation goes only to its author, and `firm_private` only to firm staff. Actions have no audience lists (`app_audience_entity_ok` has no `action` case) and firm staff have no department limits, so "may read the action" holds. The deputy reads every project of the client (`app_is_client_lead` includes `is_deputy`, 0051). `action.blocked` is not a `copy_lead_alert` kind, so the deputy is not told twice. `mail_action_notification` does not mail this kind. The notifications list reads titles under the reader's own RLS (`services/notifications.ts:64-73`). `transitionAction` is the only path to `blocked`. Every caller who can make that move passes the `app_can_see_action` check, so no legitimate transition is broken by the raise.
- **Grants (probe 5b).** `app_user_shut_out_of_meeting` and `check_meeting_invitee` are owner-only, and a direct call as `selah_app` is denied. `app_meeting_shut_out`, `app_send_meeting_invites` and `app_tell_firm_stuck` are owner plus `selah_app`. `app_meeting_mail_ok` is owner-only, as before. All new definers set `search_path = public, pg_temp`. No policies are added, so there is no RESTRICTIVE/PERMISSIVE risk.
- **Messages.** All new keys exist in both `en.json` and `ar.json`.
